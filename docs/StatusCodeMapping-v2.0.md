## What changed vs previous versions

This is the first dedicated feature doc for HTTP/gRPC status mapping at the v2.0 documentation baseline.

Notable baseline behavior carried from late v1.3.x:

- Nil Fault maps to success: HTTP `200`, gRPC `OK` (fixed in 1.3.4).
- Mapping rules by kind / error code are otherwise unchanged for v2.0.

No v2.0-specific breaking change to these mapping functions.

Within 2.0.x (release 2.0.4):

- Docs / code refer to correctly spelled `ILLEGALSTATE_ERRCODE_EXPECTATION_FAILED` for expectation-failed overrides (deprecated misspelled alias still works; same string value).

## TLDR

- Use `GetHttpStatusCodeForFault(fault)` / `GetGrpcStatusCodeForFault(fault)` (or the `Fault` method wrappers) when building an error response.
- Non-public Faults always map to internal failure: HTTP `500`, gRPC `INTERNAL`.
- For public Faults, kind sets the default; some error codes refine the status further.
- Prefer converting with [PublicFaultConversion](PublicFaultConversion-v2.0.md) before status mapping if the Fault is not yet public.

## API


Aliases on the Fault interface:

- `fault.GetHttpStatusCode()`
- `fault.GetGrpcStatusCode()`

## Shared rules

- `fault == nil`
  - HTTP → `200`
  - gRPC → `codes.OK`
- `fault.IsPublic() == false`
  - HTTP → `500`
  - gRPC → `codes.Internal`
  - kind / error codes are ignored on purpose (do not leak classification of unsafe errors)
- Public Fault with no more specific rule → stays on the function’s default internal status (`500` / `Internal`) until a kind case matches

## HTTP mapping (public Faults)

Defaults by kind:

- `AuthenticationFault` → `401`
- `AuthorizationFault` → `403`
- `ResourceNotFoundFault` → `404`
- `ConstraintViolationFault` → `412`
- `ValidationFault` → `400`
- `NotImplementedFault` → `501`
- `IllegalStateFault` → remains `500` unless an error-code override below matches
- `RuntimeFault` → `500` (no dedicated case)

Error-code overrides:

- `ConstraintViolationFault`
  - `CONSTRAINTVIOLATION_ERRCODE_ID_ALREADY_TAKEN` or `CONSTRAINTVIOLATION_ERRCODE_ALREADY_EXIST` → `409`
  - `CONSTRAINTVIOLATION_ERRCODE_DOES_NOT_EXIST` → `404`
- `IllegalStateFault`
  - `ILLEGALSTATE_ERRCODE_DEPENDENCY_UNAVAILABLE` or `ILLEGALSTATE_ERRCODE_EXHAUSTED` or `ILLEGALSTATE_ERRCODE_TIMED_OUT` → `503`
  - `ILLEGALSTATE_ERRCODE_EXPECTATION_FAILED` → `412`

## gRPC mapping (public Faults)

Defaults by kind:

- `AuthenticationFault` → `Unauthenticated`
- `AuthorizationFault` → `PermissionDenied`
- `ResourceNotFoundFault` → `NotFound`
- `ConstraintViolationFault` → `FailedPrecondition`
- `ValidationFault` → `InvalidArgument`
- `NotImplementedFault` → `Unimplemented`
- `IllegalStateFault` → remains `Internal` unless an error-code override below matches
- `RuntimeFault` → `Internal` (no dedicated case)

Error-code overrides:

- `ConstraintViolationFault`
  - `CONSTRAINTVIOLATION_ERRCODE_ID_ALREADY_TAKEN` or `CONSTRAINTVIOLATION_ERRCODE_ALREADY_EXIST` → `AlreadyExists`
  - `CONSTRAINTVIOLATION_ERRCODE_DOES_NOT_EXIST` → `NotFound`
- `IllegalStateFault`
  - `ILLEGALSTATE_ERRCODE_DEPENDENCY_UNAVAILABLE` or `ILLEGALSTATE_ERRCODE_TIMED_OUT` → `Unavailable`
  - `ILLEGALSTATE_ERRCODE_EXHAUSTED` → `ResourceExhausted`
  - `ILLEGALSTATE_ERRCODE_EXPECTATION_FAILED` → `FailedPrecondition`

## Practical notes

- Kind alone is often enough; attach the listed error codes when you need the finer statuses (conflict vs precondition, unavailable vs exhausted, etc.).
- After `NewPublicFaultFromAnyError`, non-whitelisted Faults become `RuntimeFault` + `ERRCODE_INTERNAL_ERROR` → status stays internal (`500` / `INTERNAL`), which is intentional.
- If you whitelist kinds during conversion, those kinds can produce the more specific statuses above.
- Status mapping does not serialize the body — combine with [FaultSerialization-v2.0.md](FaultSerialization-v2.0.md) for HTTP JSON error payloads.
