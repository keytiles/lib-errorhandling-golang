## What changed vs previous versions

This is the first dedicated feature doc for Fault JSON serialization at the v2.0 documentation baseline.

- Natural / full JSON forms, public-only defense, and `SerializationOption`s are part of this baseline as implemented on `Fault`.
- No v2.0-specific breaking change to serialization APIs relative to late v1.3.x.

## TLDR

- Use `ToNaturalJSON` for a compact client-facing error JSON (single `message`).
- Use `ToFullJSON` when you also want `messagesByAudience` exposed in the payload.
- By default only **public** Faults serialize for real; non-public Faults return a blanked / defensive form unless you pass `AllowNonPublicSerialization`.
- Cause and call stack are **never** included in either JSON form.
- Optional options: resolve `{var}` placeholders, leave those vars in labels, pretty-print.

## API

On `Fault`:

```go
ToNaturalJSON(forAudience string, options ...SerializationOption) ([]byte, error)
ToFullJSON(options ...SerializationOption) ([]byte, error)
```

Package-level aliases (same behavior, including nil-safe path):

```go
GetFaultAsNaturalJSON(fault Fault, forAudience string, options ...SerializationOption) ([]byte, error)
GetFaultAsFullJSON(fault Fault, options ...SerializationOption) ([]byte, error)
```

## Serialization options

`SerializationOption` values (pass any combination):

- `ResolveMessages` — resolve `{var}` placeholders from labels into the emitted message(s). By default, keys used only as message variables are then **removed** from the emitted labels map.
- `LeaveMessageVarsInLabels` — when used together with `ResolveMessages`, keep those variable keys in the emitted labels.
- `PrettyPrint` — indent JSON with tabs / line breaks.
- `AllowNonPublicSerialization` — disable the public-only defense and serialize a non-public Fault’s content.

## Public-only defense

Without `AllowNonPublicSerialization`:

- Non-public Fault → defensive blank form (not the real message/codes/labels). Retryable may still be inherited into the blank natural/full form.
- Public Fault → real content according to the chosen form / options.
- Nil Fault → empty / placeholder form (`kind` like `"NaN"`, empty message/codes/labels).

Always convert at the boundary first ([PublicFaultConversion-v2.0.md](PublicFaultConversion-v2.0.md)) if you intend to return JSON to clients.

## Natural JSON (`ToNaturalJSON`)

Shape:

```json
{
  "kind": "<FaultKind>",
  "message": "<default or audience message>",
  "isRetryable": true,
  "errorCodes": ["..."],
  "labels": { "...": "..." }
}
```

Parameters:

- `forAudience`
  - empty string → default message template / resolved default message
  - non-empty → that audience’s template / resolved message (e.g. `MSGAUDIENCE_USER`)

What is intentionally omitted:

- cause
- call stack / source
- full `messagesByAudience` map (only one message field)

## Full JSON (`ToFullJSON`)

Serializes more of the Fault’s message structure:

- default message field (`message` / message template field on the struct)
- `messagesByAudience`
- `kind`, `isRetryable`, `errorCodes`, `labels`

Still omitted:

- cause
- call stack / source
- internal unexported fields

Use this when clients or gateways need multiple audience messages; prefer natural JSON for typical HTTP API error bodies.

## Examples

Natural JSON for users, resolved message, pretty:

```go
body, err := fault.ToNaturalJSON(
    kt_errors.MSGAUDIENCE_USER,
    kt_errors.ResolveMessages,
    kt_errors.PrettyPrint,
)
```

Full JSON without stripping message-var labels:

```go
body, err := kt_errors.GetFaultAsFullJSON(
    fault,
    kt_errors.ResolveMessages,
    kt_errors.LeaveMessageVarsInLabels,
)
```

## Practical notes

- Pair with [StatusCodeMapping-v2.0.md](StatusCodeMapping-v2.0.md) for the response status; serialization only builds the body.
- If you resolve messages and do not pass `LeaveMessageVarsInLabels`, clients see clean labels without duplicated `{var}` keys already baked into `message`.
- Non-public serialization with `AllowNonPublicSerialization` is for trusted/internal tooling only — not for end-user responses.
